# DESIGN_PRINCIPLES — визуальная система

## Core

- Mobile-first.
- Базовый viewport: `390×844`.
- Рабочий диапазон: примерно `320–500px` по ширине.
- На desktop допустим центрированный mobile game viewport.
- Пиксельная/cozy эстетика — язык интерфейса, но продукт не должен выглядеть как дешёвый wireframe.

## Desired palette / semantics

Точные цвета могут эволюционировать. Смысловые группы:

- морской/голубой — вода, наблюдение, технологии;
- природный зелёный — здоровая территория/успех;
- песочный/кремовый — берег, панели, спокойный фон;
- жёлтый/оранжевый — предупреждение/загрязнение;
- тёмно-синий — космос/ночное технологическое окружение;
- красный использовать осторожно — критическое состояние, не постоянный декор.

## Pixel feel without bad UX

Можно использовать:

- чёткие края;
- небольшие радиусы или ступенчатые формы;
- pixel-like borders/shadows;
- CSS/SVG тайлы;
- геометрические иконки;
- limited motion;
- крупные touch targets;
- игровые диалоги и bottom sheets.

Не жертвовать читабельностью ради «пиксельности».

## Avoid

- glassmorphism как основной язык;
- типичный SaaS dashboard;
- огромные корпоративные cards;
- мелкий текст;
- слишком много HUD;
- декоративные анимации, которые мешают нажатию;
- визуальные стили разных экранов, будто их делали разные продукты.

## Hierarchy

На каждом экране за 1–2 секунды должно быть понятно:

1. где пользователь;
2. что произошло;
3. что важно;
4. что можно сделать дальше.

## Motion

Анимация должна делать хотя бы одно:

- объяснять переход масштаба (космос → территория);
- направлять внимание;
- подтверждать действие;
- показывать анализ/сканирование;
- показывать изменение мира;
- усиливать эмоциональный payoff.

Если она только «двигается красиво» и ухудшает performance/pacing — удалить или упростить.

## Asset strategy now

Пока финальных ассетов нет:

- использовать CSS/SVG/procedural placeholders;
- доводить их до презентабельного состояния;
- сохранять единый GameAsset/registry layer;
- не хардкодить конкретное изображение в gameplay logic.

## Asset strategy later

При подключении PNG/WebP/SVG/sprites менять преимущественно asset config/render layer. Игровая логика не должна знать, placeholder это или финальный sprite.

## Screenshot review

После серьёзного visual change сравнивать ключевые экраны как статичные кадры:

- первый экран;
- карта;
- проблемная зона;
- DZZ/scan;
- decision;
- result;
- возвращение на изменённую карту.

Искать: слабую иерархию, пустоты, перегруз, наложения, несогласованность, мелкие touch targets, «SaaS drift».
