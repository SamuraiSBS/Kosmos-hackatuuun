# HACKATHON_STRATEGY — стратегия на первое место

## North Star

Не «самая большая программа», а **самая убедительная работа в коротком формате защиты**.

## Приоритеты

1. Demo Readiness.
2. Case Fit.
3. DZZ / Educational Clarity.
4. Wow Effect / Visual Quality.
5. Originality.
6. Mobile UX / First-time Clarity.
7. Практическая экологическая осмысленность.
8. Game Engagement.
9. Technical Stability / Performance.
10. Technical Complexity — только как средство.

## Что должно произойти в голове жюри

В идеале после показа жюри может одной фразой пересказать идею:

> «Они превратили образовательный проект по спутниковому мониторингу загрязнений побережий в понятную интерактивную игру, где ты сам находишь проблему по данным, принимаешь решение и видишь эффект».

Если пересказ получается «у них прикольная пиксельная ферма», продукт требует realignment.

## Demo-first rule

Любая значимая функция должна пройти вопрос:

> Будет ли её ценность видна/понятна за время защиты?

Если нет, она не обязательно бесполезна, но обычно проигрывает по приоритету фиче, которую жюри реально увидит.

## Четыре слоя сильной защиты

### 1. Hook
Первые секунды должны выглядеть намеренно и запоминающеся.

### 2. Problem comprehension
Пользователь/жюри быстро понимает экологическую проблему и цель.

### 3. Technology comprehension
Взаимодействие показывает роль ДЗЗ, а не просто произносит слово «спутник».

### 4. Consequence
Решение меняет мир и формирует ощущение результата.

## Time budget продукта

Главный интерактивный путь должен быть достаточно коротким для уверенной демонстрации. Стартовый ориентир: ключевая ценность становится понятна в первые 30–60 секунд, а один законченный loop проходится примерно за 1.5–3 минуты.

Оркестратор может изменить цифры после фактического browser timing.

## Что обычно НЕ выигрывает нам защиту

- скрытая инфраструктура, которую нельзя объяснить/показать;
- преждевременный backend;
- сложная абстракция ради абстракции;
- огромное количество незаконченных миссий;
- множество настроек;
- второстепенные экраны, которые не участвуют в demo;
- высокая техническая сложность при слабом UX.

## Правило последних итераций

Чем ближе проект к FREEZE, тем выше цена regression. Крупные изменения должны давать очевидный gain. Если проект стабилен и сильный — polish > feature creep.
