# AGENTS.md — конституция проекта «Чистый берег»

Этот файл обязателен для главного оркестратора и всех делегированных агентов.

## Mission

Создать наиболее сильное возможное решение кейса №1 «Чистый берег» КосмоХакатона: приложение, которое популяризирует образовательный проект и через понятное интерактивное взаимодействие показывает экологический анализ поверхности планеты с применением ДЗЗ.

**North Star:** вероятность первого места на защите, а не количество функций.

## Source of truth

Приоритет источников:

1. `docs/CASE_SOURCE.md` + актуальные официальные источники;
2. `docs/PRODUCT_VISION.md`;
3. фактическое поведение работающего приложения;
4. `docs/HACKATHON_STRATEGY.md` / `docs/HACKATHON_TIMEBOX.md` / `docs/DEMO_FLOW.md`;
5. текущий backlog/decisions;
6. `original/INITIAL_MVP_PLAN.md` как историческая техническая база.

Если исходный MVP расходится с кейсом — сохранять полезную архитектуру, но менять продуктовую семантику.

## Autonomy

Оркестратор имеет право самостоятельно принимать обычные продуктовые/UX/технические решения и не должен просить подтверждения там, где можно принять разумное решение.

Передавая задачу субагенту, дай ему достаточный контекст и конкретный deliverable. Субагент не принимает финальное продуктовое решение: он консультирует оркестратора.

## Non-negotiables

- Не уходить в кейс мониторинга вегетации.
- ДЗЗ не должно быть декоративным словом: роль данных должна быть понятна пользователю.
- Продукт должен популяризировать именно образовательный проект «Чистый берег», а не только тему мусора вообще.
- Mobile-first.
- Critical demo-flow должен работать без debug mode.
- Не объявлять UI проверенным, если он не был фактически открыт/пройден доступным способом.
- Не уничтожать пользовательские незакоммиченные изменения.
- Не ждать финальных ассетов: использовать заменяемые CSS/SVG/placeholders.
- Не делать feature creep без высокого impact.
- Соблюдать официальный СТОП-КОД и не использовать автономность для обхода правил хакатона.

## Product loop

Предпочтительный базовый цикл:

`обнаружить проблему → увидеть данные → разобраться → принять решение → увидеть последствие → получить образовательный вывод/прогресс`

Конкретная реализация может эволюционировать, если это улучшает кейс и demo.

## Decision rule

Перед значимым изменением ответить себе:

1. Как это помогает официальной задаче?
2. Увидит/почувствует ли это жюри в короткой демонстрации?
3. Станет ли пользователю понятнее роль ДЗЗ/проекта?
4. Не ломает ли это critical flow?
5. Есть ли более дешёвый способ получить тот же impact?

Если ответы слабые — не реализовывать или понизить приоритет.

## Quality loop

Существенное изменение считается завершённым только после максимально доступного цикла:

`code → typecheck/lint → tests → build → browser/mobile → critical flow → console → visual review → case review → commit`

## Git

См. `docs/GIT_POLICY.md`. Любой рискованный редизайн — после checkpoint. Не использовать destructive reset против неизвестной работы пользователя.

## Documentation

Документы — долговременная память, а не бюрократия. Обновлять `STATE_OF_PROJECT`, `BACKLOG`, `DECISIONS`, `QUALITY_SCORECARD`, `ASSET_REQUESTS` когда факты реально изменились.

## Escalation

Не спрашивать пользователя по обычным решениям. Если есть внешняя блокировка, пометить только конкретную задачу `BLOCKED_EXTERNAL` и продолжить другой high-impact work.

## Definition of success

Пользователь/жюри без дополнительного объяснения понимает:

- что это «Чистый берег»;
- в чём экологическая проблема;
- зачем здесь ДЗЗ и геоданные;
- что он сам делает в продукте;
- как действие связано с анализом данных;
- как технология помогает реальной природоохранной работе;
- почему хочется узнать/пройти больше.
